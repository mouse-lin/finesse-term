# 检索策略

检索是本地的，零网络依赖，几毫秒返回。**成本不是理由 —— 不确定就查，别凭印象编。**

---

## 一、先拆子句，再查

一句口语里通常藏着两三件事。整句丢进去只会命中最显眼的那一件。

```bash
# ❌ 整句
node scripts/term.mjs find --q "鼠标放上去变个色，点下去也要有反馈，另外底下按钮被挡住了"

# ✅ 拆开
node scripts/term.mjs find \
  --q "鼠标放上去变个色" \
  --q "点下去也要有反馈" \
  --q "底下按钮被挡住了"
```

拆的依据是**逗号和「另外 / 还有 / 顺便」**，不是语法。每个子句描述一件事。

`--q` 最多 5 次。超过 5 件事，说明用户在提一整个需求，那时该先把活干完，回头只挑最值得说的 1–3 条。

---

## 二、别把整段需求当搜索词

用户贴过来的一整段需求文档、一整个 Agent 回复、一段代码 —— 都不要直接丢进 `--q`。

先自己读，定位到**用户在说哪件具体的界面事**，用那几个字去查。检索器按双字组覆盖率打分，长文本会把分数摊薄到所有词条上，返回一堆低分噪音。

---

## 三、限定 surface 减噪

已知场景时限定，能显著提高准确率：

```bash
node scripts/term.mjs find --q "弹出来的面板" --surface h5    # 得到 底部弹层
node scripts/term.mjs find --q "弹出来的面板" --surface web   # 得到 气泡卡片 / 模态框
```

判断依据：用户提过「手机」「H5」「微信」「小程序里的网页」「移动端」，或者项目本身就是 H5 → `--surface h5`。不确定就不加，全库查。

---

## 四、命中为零是正常结果

```json
{ "count": 0, "candidates": [] }
```

这不是失败。它说明这一轮用户**没有描述任何值得命名的界面行为** —— 他可能在聊接口、聊数据、或者只是在正常说话。

按门禁一：**保持沉默，照常干活。** 不要降低标准去凑一条，也不要换十个说法反复查同一件事。

---

## 五、低分候选怎么办

`find` 的入选门槛是 30 分。分数的含义大致是：

| 分段 | 含义 | 怎么办 |
|:---|:---|:---|
| ≥ 60 | 用户几乎原话说中了触发词 | 直接用 |
| 40–60 | 说法被打散在句子里，但覆盖率高 | 用，但先确认语境对得上 |
| 30–40 | 擦边 | **读一遍 `plain`，确认真的在说这件事再用** |

`match.matched` 里写着是哪个字段的哪一条命中的（`trigger:按钮被挡住`）。这既是门禁一要求的证据，也是你自查是否误命中的依据 —— 命中的那几个字如果和用户的意思对不上，就是噪音，丢掉。

---

## 六、拿到结果之后

1. **看 `pairs`** —— 非 `--brief` 输出已经把搭档的标题带出来了，不用再查。门禁二要求成对说出。
2. **看 `trap`** —— 多数时候它比 `plain` 更值得说给用户听。
3. **抄 `say`** —— 需要改写需求时，这句话可以直接用，或者按用户的原意微调。
4. **不要输出 `match` 和 `id`** —— 那是给你看的，不是给用户看的。

---

## 七、只用库里有的

库里没有的术语，就用大白话把事情说清楚，**不要临时包装出一个术语**。

编出来的术语比不说更糟：用户会拿它去搜、去问别人、去写进需求文档，然后发现没人知道那是什么。

如果反复遇到某个概念库里没有，那是**加词条**的信号（见 `entry-format.md`），不是即兴发挥的信号。
